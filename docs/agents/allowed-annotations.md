# Allowed comment patterns

`spec.comments.allowedAnnotations` in `.koment/policy.yaml` extends the
five intrinsic comment classes (`toolchain-directive`, `generated-marker`,
`upstream-link`, `deprecated`, `public-api`) with repository-specific
patterns. Each entry is a Go regexp matched against the comment body
after leading-marker and surrounding-whitespace stripping.

This page documents the shape and ships common examples. Add a pattern
when a comment is required by a tool the repository uses, not when it
is convenient for a contributor. The strict check still rejects every
other comment — there is no path-wide exemption here.

## Shape

```yaml
spec:
  comments:
    allowedAnnotations:
      - "<regexp>"
```

- The list is matched in order; the first pattern that matches wins.
- Patterns are anchored implicitly at both ends. `^` and `$` are
  unnecessary; a partial match still passes.
- Patterns are Go regexp, not glob. `*` matches any run of characters
  with no need to escape; literal `.`, `(`, `)` and `|` need to be
  escaped as `\.`, `\(`, `\)`, `\|` (or use `[.]`, `[(]`, `[)]`,
  `[|]`).
- Patterns are validated when `koment bootstrap` reads the policy.
  A bad pattern fails the install, not the first commit.
- Both the pre-tool hook and `koment comments check` consult the
  field. Adding an entry does not require any other change.
- The pattern matches against the comment body with leading comment
  markers (`//`, `/*`, `*`) stripped, not the raw source text. Write
  patterns on the body, not on the comment syntax. `// renovate:
  enable` matches the pattern `renovate[\s:]`, not `# renovate[\s:]`
  — the `#` only appears in the original syntax, not in the stripped
  body.

## Common patterns

Copy and adapt. Each is a starting point — narrow it to your
repository's exact wording if you need to.

### Renovate

```yaml
allowedAnnotations:
  - "renovate[\\s:]"
```

Matches `// renovate:`, `// renovate ` and any other comment whose
body introduces a Renovate configuration block.

### Protocol-buffer generated files

```yaml
allowedAnnotations:
  - "Code generated by protoc-gen.*DO NOT EDIT"
```

Matches the standard `protoc-gen-*` marker; `Code generated` plus
`DO NOT EDIT` is the conventional wording. Adjust the `protoc-gen.*`
portion to the generators you actually use.

### SPDX license headers

```yaml
allowedAnnotations:
  - "SPDX-License-Identifier:"
```

Matches any comment that declares an SPDX license identifier.

### go-swagger annotations

```yaml
allowedAnnotations:
  - "swagger:model"
  - "swagger:route"
  - "swagger:operation"
  - "swagger:parameters"
  - "swagger:response"
  - "swagger:strfmt"
```

Each on its own line, or combined as `swagger:(model|route|operation|…)`
if you prefer one entry.

### Generated bindings and clients

```yaml
allowedAnnotations:
  - "Code generated by .* DO NOT EDIT"
  - "Autogenerated by .* DO NOT EDIT"
```

Broader than the intrinsic `generated-marker` (which requires the exact
phrases `Code generated` and `DO NOT EDIT.`). Use these when the
generator's marker uses different verbs (`Autogenerated`,
`Auto-generated`, `DO NOT MODIFY`).

### OpenAPI / AsyncAPI codegen

```yaml
allowedAnnotations:
  - "Generated by openapi-generator.*DO NOT EDIT"
  - "Generated by asyncapi.*DO NOT EDIT"
```

### Custom house style

```yaml
allowedAnnotations:
  - "mycompany-internal:"
```

A repository-owned marker that nothing upstream enforces. The
`mycompany-internal:` shape is the convention; the project does not
recognise it.

## What not to put here

- **Anything you want a future reader to see.** That is what `koment
  add` is for.
- **A restatement of an intrinsic.** `go:`, `+build`, `nolint:`,
  `Deprecated:`, godoc on exported identifiers — these are
  intrinsic classes enabled in `spec.comments.intrinsic`, not
  patterns to repeat in `allowedAnnotations`. The intrinsic
  classifier checks them first and short-circuits before the
  pattern list runs.
- **Anything path-shaped.** `allowedAnnotations` is a content
  match, not a path exemption. Generated and vendored files are
  declared in `spec.comments.generatedPaths` and
  `spec.comments.vendoredPaths`, which skip enforcement entirely
  for matching paths.

## When the pattern set stops fitting

If a future survey shows a small set of widely-used conventions whose
exact wording keeps drifting, the addition is minor and additive:
`allowedAnnotations` accepts either a regexp string or an object with
a `class:` key referencing a vocabulary name. Today only the regexp
form ships — see ADR 0124 for the rationale and the path forward.
