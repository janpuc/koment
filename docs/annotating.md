# Writing good annotations

The syntax takes a minute. The judgement is the hard part, and it decides
whether anyone trusts the store in six months.

## The test

> Would a competent stranger — or an agent — look at this code and change it in
> a way that breaks something they couldn't have known about?

If yes, annotate it. If no, don't.

An annotation on something self-evident is worse than nothing twice over: it
trains readers to skim past the ones that matter, and it is one more thing that
can drift.

## Annotate the surprise, not the code

The code already says what it does. An annotation that narrates it is a comment
with extra steps, and it goes stale the same way.

```
✗ Subtracts clockSkew from the current time before comparing.
✓ Without the skew subtraction, clients whose clock runs a few seconds fast
  are logged out mid-request. Bit us in #412.
```

The first is readable from the code. The second is not readable from anywhere.

## Say what happens if it changes

The most valuable annotations are the ones that stop a future edit. Make the
consequence explicit.

```
✓ Do not switch this to 0.0.0.0 to make containers easier. There is no
  authentication on this port, so that publishes every annotation in the
  repository to the local network.

✓ serve() must be the last call: it blocks until the process is signalled.
  Anything after it never runs.
```

Both tell a reader what they were about to break.

## Pick the kind honestly

| kind | for |
|---|---|
| `why` | this approach over the obvious alternative |
| `gotcha` | a trap someone already fell into |
| `invariant` | something that must stay true, and what breaks if it doesn't |
| `anti-pattern` | a thing that was tried and does not work |

Four, deliberately. A free-form kind field becomes a junk drawer, and the value
of a small vocabulary is that `koment list --kind invariant` returns something
worth reading.

## Give the headline a sentence worth reading

The headline is the one line every reader sees — beside the code, in the panel,
in the hover, in the search index. `spec.title` is optional in the schema, and
that is deliberate: a record written before titles existed still has to render
something. When the field is empty, `Annotation.Headline()` shows the first
sentence of the body, shortened at a word boundary and capped at 72 characters
with a trailing `…` when it would otherwise cut through one.

The derivation is computed on read and never written back. A derived title
stored in the record would be a second copy of the body that could drift from
it, which is the failure this project exists to prevent.

`koment add` warns when `--title` is empty so the consequence is clear at write
time. The warning is not an error: a quick note with a tight first sentence
renders exactly as the author intended.

```
✓ Rotation keeps the previous key   (explicit, one line)
○ Without the skew subtraction ...  (derived, shortened with …)
✗ Re: ticket #12345 — see the co…  (derived, but the first sentence was not a title)
```

A title is work, and a bad one is worse than the derived fallback because it
hides the sentence it replaced. When the body's first sentence is a real,
informative line, leave the field empty; the headline will be the same
sentence you would have written. When it is not, write one.

## Anchor to something stable

The excerpt must be unique in the file, and every edit to it produces drift.
Both facts push the same way: anchor to the most stable distinctive line
available.

```
✓ func Address(address string) (string, error) {     signature — stable
✓ if token.Expiry.Before(now.Add(-clockSkew)) {      the condition itself

✗ 	}                                                 not unique
✗ 	return net.JoinHostPort("127.0.0.1", port), nil   changes on any refactor
```

A function signature is usually the best anchor: it changes rarely, it is
unique, and it is where a reader looks first.

Use file scope — omit `--excerpt` — when the point is about the file as a whole:

```sh
koment add internal/generated/api.go --kind why \
    --body 'Generated by oapi-codegen. Edit the spec, not this.'
```

File-scoped annotations only drift on rename or delete.

## Write for someone who wasn't there

Reference the issue, the incident, the benchmark. "Bit us in #412" is worth more
than "this is important", because it can be looked up.

Prose, complete sentences. It gets read by people and by models, and both do
better with paragraphs than with fragments. koment wraps it for you.

## When to reach for something else

koment holds knowledge bound to a **place in the code**. Other things belong
elsewhere:

- **A project-wide decision** — an ADR. It has no anchoring problem and no drift.
- **How to use the thing** — the README or the API docs.
- **Something that would be clearer as better code** — rename the variable,
  extract the function. An annotation explaining a bad name is a bad name with a
  note attached.

That last one matters most. Try, in order: rename it; extract a function whose
name is the annotation you were about to write; introduce a named constant;
restructure so the invariant is obvious. Only when all four fail has an
annotation earned its place.

## Maintaining them

`koment check` tells you when one stopped resolving. When it does, read it and
decide:

- **still true** → `koment reanchor <id> --excerpt '<new text>'`
- **file moved** → `koment reanchor <id> --file <new path>`
- **no longer true** → delete it; it did its job

Deleting an annotation to make the build green without reading it is the one
genuinely wrong move. That is the failure this tool exists to prevent.
