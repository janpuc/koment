# 0014 — Export static HTML, for the demo site only

Date: 2026-07-31
Status: Accepted

Narrows one alternative rejected in ADR 0013. The rest of 0013 stands: `koment
ui` remains the way you read your own annotations, and it stays a live server.

## Context

ADR 0013 rejected a static site generator with one sentence: *"it goes stale the
moment the code changes, which is the failure mode koment exists to prevent."*

That reasoning is correct for the tool and wrong for a shop window. It answers
"how should someone read the annotations in their own repository" — where
staleness is fatal — but koment also has to answer "what is this, and why would
I want it" to somebody who has not installed anything. A README screenshot is a
worse answer than the real interface, and asking a stranger to `go install` a
tool before they can see what it looks like is a poor trade.

The distinction that makes both true: a demo is a **snapshot of a known commit**,
not a view of a working tree. It is not claiming to be current for any
repository the reader has. It is claiming to be an accurate rendering of
koment's own `main`, which is exactly what CI can guarantee.

## Decision

Add `koment export --out <dir>`, which renders the same templates and the same
`anchor.Resolve` results as `koment ui` into static HTML.

Its only sanctioned use is the demo site. GitHub Pages publishes koment's own
annotations, regenerated by CI on every push to `main`, so the published
snapshot is never older than the commit it names.

Three properties keep the ADR 0013 objection answered:

- Every exported page carries a banner naming the commit it was built from and
  stating that it is a snapshot. It never presents itself as live.
- The workflow runs `koment check` before exporting. A build with unresolved
  drift does not publish.
- The docs point users at `koment ui` for their own code. `export` is documented
  as the mechanism behind the demo, not as a way to read your annotations.

## Consequences

- Someone can see the tool before installing it, which is the point.
- The demo is a genuine correctness signal, not marketing: it is generated by
  the real code path from the real store, so a rendering bug shows up publicly.
  Publishing it on every push makes the UI's output part of what CI exercises.
- **Publishing the demo publishes koment's own source excerpts and every
  annotation body.** For this repository that is intended. Anyone pointing
  `export` at a private codebase and deploying the result is publishing their
  code and their reasoning — the docs say so plainly.
- A second rendering path to keep working. Kept honest by sharing the view model
  and templates with the server; only link generation differs, since a static
  tree needs relative hrefs and a served tree does not.
- Static output means no per-request resolution, so the drift shown is drift at
  build time. Accurate for a snapshot, and precisely why this is not the read
  path for real work.

## Alternatives rejected

- **No demo; a screenshot in the README.** Cheapest. Rejected because a
  screenshot cannot be clicked, goes stale silently with nothing to detect it,
  and a tool whose whole argument is "stale representations are dangerous"
  should not lead with one.
- **A hosted live instance of `koment ui`.** Truest to the product, and it would
  need a server, a deployment, an uptime story and an unauthenticated
  network-exposed port — everything ADR 0011 was careful about, in exchange for
  showing a repository that does not change between deploys anyway.
- **Recording a video or GIF.** Common and effective. Rejected as strictly worse
  than the real HTML here, which costs about the same to produce, can be
  navigated, and cannot drift from the code because CI regenerates it.
- **Making `export` a first-class documented feature for any repository.** The
  obvious generalisation. Rejected deliberately: it invites exactly the
  stale-snapshot workflow ADR 0013 rejected, and it would put a "publish your
  private code" footgun in the main command surface. It stays scoped to the
  demo, and the docs do not offer it as an alternative to `koment ui`.
