# 0124 — `koment bootstrap`, a stronger agent contract, and a user-configurable comment allow-list

Date: 2026-08-06
Status: Accepted
Supersedes: portions of [0108](0108-layer-agent-guidance-behind-an-authoritative-policy-gate.md) (the install/check shape and the contract text)

## Context

ADR 0108 made `koment agents install` write the strict `.koment/policy.yaml`
and a managed contract into every supported adapter, and made
`koment agents check` the drift gate on the protected branch. Three things
have surfaced since it was accepted.

**1. The onboarding UX is not an onboarding.** A new user runs
`koment agents install` and gets every adapter the project supports,
including ones they do not use. The repository ends up with
`.cursor/mcp.json`, `.codex/hooks.json`, `.opencode/plugins/koment.js` and
so on for clients nobody on the team has installed. This is the opposite
of "don't pollute the repo". The user has to read source to discover
which file belongs to which client, and uninstalling an adapter means
hand-deleting files.

**2. The contract text is too soft for what it is.** The procedure in
`agentpolicy.Contract()` reads like guidance — "call", "prefer", "treat".
The contract is the only thing a supporting client sees, and the only
thing the pre-tool hook reminds the agent of before a write. Soft wording
is a fair signal that the rule is optional. RFC 2119 keywords (`MUST`,
`MUST NOT`, `REQUIRED`, `FORBIDDEN`) exist for exactly this case and cost
nothing; the comment policy already uses "FORBIDDEN" in user-facing copy.

**3. The comment allow-list is closed and Go-shaped.** The intrinsic
classes in `policy.Intrinsic*` are hardcoded
(`internal/policy/policy.go:34`) and the hook classifier
`intrinsicPatchComment` (`internal/agentpolicy/hooks.go:126`) hardcodes
Go-flavoured prefixes (`go:`, `+build`, `nolint`, `lint:`, `revive:`,
`gosec`, `export `, `#cgo`). A repository that legitimately needs `# renovate`
markers, `Code generated by protoc` lines, SPDX headers or a CI bot's
house style either disables the strict check or hand-edits the policy
file in a way `Validate()` rejects. ADR 0108 explicitly rejects a
path-wide exemption, but it does not reject a vocabulary extension —
and a closed vocabulary is not the same thing as a strict check.

The three concerns are one product gap: onboarding is a procedure, not a
command; the procedure is a hint, not a contract; and the contract's
allow-list is a fixed enum that does not match how repositories actually
use comments.

## Decision

Three changes, shipped together.

### A. Add `koment bootstrap` as the human-facing onboarding command

`koment bootstrap` is a new top-level command. It does what
`koment agents install` does today, plus:

- If `.koment/policy.yaml` does not exist, write it from `policy.Default()`
  before installing adapters, so the contract body is parameterised by
  the same policy the rest of the system reads.
- Resolve which adapters to install in this order:
  1. `--agents claude,opencode,…` (explicit, non-interactive).
  2. `--all` (every supported adapter).
  3. `--policy-only` (skip adapter writes; the policy is still installed
     if absent).
  4. The current policy's `spec.agents.adapters` if the policy file
     already exists.
  5. Interactive prompt per adapter when stdout is a TTY and no flag
     resolved the list.
  6. Error and a pointer to `--agents` or `--all` when none of the
     above applies (no flag, no policy, no TTY).
- Refuse to remove an adapter the user did not name on this invocation.
  Re-running `koment bootstrap` against an already-bootstrapped repo
  refreshes managed blocks in the selected adapters and leaves every
  non-selected adapter file untouched on disk.
- Seed or refresh a managed block in `CONTRIBUTING.md` that points human
  contributors at the agent contract (in `AGENTS.md` and the per-client
  adapters) and the three required checks (`koment check`,
  `koment comments check`, `koment agents check`). When
  `CONTRIBUTING.md` does not exist, the bootstrap creates it with the
  managed block as the entire body; when it does, the block is inserted
  or replaced inside the same `<!-- koment:managed-start -->` …
  `<!-- koment:managed-end -->` markers every other adapter uses. The
  block is human-oriented prose and never overlaps the agent contract.
  The block is part of the same install/refresh/drift machinery as every
  other adapter; `koment agents check` (and therefore the CI gate)
  fails if it drifts.

  The block body is generated by `agentpolicy.contributingBlock(policy)`
  and reads:

  ```markdown
  ## Comment policy

  This repository keeps explanatory rationale out of source. Inline
  comments are restricted to toolchain directives, generated-file
  markers, links to upstream constraints, `Deprecated:` markers on
  exported identifiers, and godoc on exported identifiers. Repository-
  specific patterns (such as `# renovate:` or `Code generated by
  protoc`) may be declared under `spec.comments.allowedAnnotations` in
  `.koment/policy.yaml`; see `docs/agents/allowed-annotations.md` for
  the shape and common examples.

  Before adding a comment, rename, extract, introduce a named type or
  constant, or restructure so the invariant is obvious from control
  flow. When rationale still needs saying, record it as a `koment`
  annotation bound to nearby code:

  ```sh
  koment add <file> --excerpt '<snippet>' --kind <kind> --body -
  ```

  See `docs/annotating.md` for the kinds and the discipline.

  ## Agent contract

  AI agents working in this repository follow a managed contract. The
  contract is generated by `koment bootstrap` and refreshed by
  `koment agents install`; it lives in `AGENTS.md` and in every
  adapter selected by `.koment/policy.yaml`. The contract is the
  same for every agent regardless of which client you use.

  ## CI gates

  Every pull request runs three checks on the protected branch:

  - `koment check` — every annotation resolves.
  - `koment comments check` — no prohibited inline comment lands.
  - `koment agents check` — every adapter still carries the managed
    contract.

  A prohibited comment cannot land even when the agent ignored every
  instruction. Local hooks make violations rare; CI makes them
  impossible.
  ```

  The block is prose for humans, not the agent contract. It never
  carries `MUST`/`MUST NOT` keywords; it states the rule once, names
  the tool that enforces it, and points at the documents that hold the
  detail.
- Print a one-line summary per changed file (`installed AGENTS.md`,
  `refreshed .cursor/mcp.json`, `policy unchanged`,
  `seeded CONTRIBUTING.md`) so the human can see what landed before
  they commit.

`koment agents install` stays as a non-interactive, scriptable alias
that resolves the adapter list from the existing policy with no prompt.
CI, Lefthook and Docker image entrypoints continue to call
`koment agents install`; humans call `koment bootstrap`. Both share
`agentpolicy.Install`; `bootstrap` adds the prompt and the policy-write
step that `agents install` already delegates to `policy.Install`.

`koment agents check` is unchanged. It remains the drift gate.

### B. Rewrite the generated contract in RFC 2119 terms

`agentpolicy.Contract()` returns a new body that uses `MUST`,
`MUST NOT`, `REQUIRED`, `FORBIDDEN` and the imperative voice. The
ordering of rules is preserved; the wording is not. New text:

```markdown
# KOMENT PROCEDURE — MANDATORY

This file is a managed contract. The repository enforces it with
client hooks and a required CI status. You MUST follow every rule.
Partial compliance is a bug.

## Before any edit or write to an existing file

- You MUST invoke `koment_get("<repository-relative path>")` via MCP
  and treat the returned annotations as the authoritative context for
  the file. An annotation whose status is `ambiguous`, `drifted` or
  `orphaned` is history, not current fact; surface it to the human
  before continuing.
- You MUST invoke `koment_search("<topic>")` before any non-obvious
  structural decision that another file may already explain.

## Adding or changing a comment is FORBIDDEN

- You MUST NOT write an ordinary inline comment in source. The
  repository classifies every comment group and rejects ordinary ones
  on the protected branch. The only exceptions are the intrinsic
  classes enabled in `.koment/policy.yaml` (toolchain directives,
  generated markers, upstream links, `// Deprecated:`, godoc on
  exported identifiers) and any additional pattern declared under
  `spec.comments.allowedAnnotations`.
- Before keeping a comment, you MUST attempt in order: rename the
  thing, extract a function whose name is the comment you were about
  to write, introduce a named type or constant, restructure so the
  invariant is obvious from control flow. If the rationale still needs
  saying, call `koment_add` bound to the code with `--excerpt` and
  record yourself honestly as an agent.
- If a comment already exists in source, you MUST call
  `koment_convert_comment` first to record it as an annotation, then
  remove the comment from source.
- Keeping an inline comment requires `koment_acknowledge_comment`
  with `acknowledge_inline_comment: true` and a human-readable body.
  The acknowledgement is auditable.

## Before you stop

- You MUST run `koment check`, `koment comments check` and
  `koment agents check`. You MUST NOT report success while any fails.
```

This text is generated, not hand-edited. It lives in Go beside the
intrinsic and principle vocabularies, so a vocabulary change and a
contract change ship together. `agentpolicy.ContractFor(policy)`
appends the stated principles exactly as today; the wording of a
principle is the only place the project still uses prose style.

The wording is enforced by `koment agents check`, which compares the
managed block byte-for-byte against the contract body returned by the
running binary. After this change every repository that already ran
`koment agents install` will see a one-time diff against the generated
block until they re-run `koment bootstrap` (or `koment agents install`)
and commit the refresh. That diff is the upgrade mechanism; it is what
makes "modify those rules from upstream" mean something.

### C. Add `spec.comments.allowedAnnotations` to the policy

`CommentsPolicy` gains one field:

```yaml
spec:
  comments:
    allowedAnnotations:
      - "# renovate[\\s:]"
      - "Code generated.*DO NOT EDIT"
      - "^SPDX-License-Identifier:"
```

Each entry is a Go regexp anchored with `^…$` against the comment body
after leading-marker and surrounding-whitespace stripping (the same
"body" the intrinsic classifier reads). The vocabulary is closed at
the syntax level — entries are validated as compilable regexp — and
open at the content level. There is no allow-list of named classes;
the body pattern is the source of truth, so a repository can match
exactly what it uses without inventing a vocabulary name.

The field is additive. An absent or empty `allowedAnnotations` is
exactly today's behaviour, and `policy.Default()` omits it. Existing
repositories do not change until they add an entry.

The hook (`agentpolicy.intrinsicPatchComment`) and the comment policy
(`commentpolicy.isIntrinsic`) both consult the field. A match returns
`true` from the intrinsic check in either path. The classifier still
runs the existing five intrinsic classes first; an
`allowedAnnotations` match is a final escape valve, not a replacement
for the strict rule.

The strict policy cannot grant a path-wide exemption (ADR 0108) and
this change does not weaken that. `allowedAnnotations` is a content
match, not a path match. A `# renovate` line in `internal/foo.go` and
a `# renovate` line in `vendor/bar.go` behave the same way — the
matcher does not see the file. Generated and vendored paths remain
declared under `spec.comments.generatedPaths` and
`spec.comments.vendoredPaths` and still skip enforcement entirely.

**Why regexp strings, not a vocabulary of named classes.** The
alternative is `allowedAnnotations: [{class: renovate}, {class: spdx}, …]`
where each `class` is a name from a closed vocabulary the project
maintains. The argument for it is the same argument ADR 0121 made for
`principles`: compile-time safety, discoverability and one-place
maintenance when a vendor's wording changes upstream. The argument
against it is the same argument AGENTS.md #11 makes for scope: do not
build until the use case exists.

- `# renovate`, `Code generated by protoc`, SPDX, swagger model markers,
  language-specific generated markers and CI bot house styles are not
  a closed set. Every new convention is an API addition, which means
  every addition is an ADR.
- The shapes are stable; the names are not. A regexp captures the
  shape, so a vendor renaming its marker (`# renovate` →
  `# renovate-bot`) is a one-line change in the repository that uses
  it, not a new vocabulary entry in this project.
- Repository-specific conventions (`// mycompany-internal: foo`) cannot
  ever be named centrally. A vocabulary that cannot hold every
  legitimate entry forces users back to regexp anyway, leaving two
  surfaces to document.

If a future survey shows a small set of widely-used conventions whose
exact wording keeps drifting, the addition is minor and additive:
`allowedAnnotations` accepts either a regexp string or an object with
a `class:` key referencing a vocabulary name. That addition does not
break repositories using string form today. For v1, regexp strings
are the entire feature, and `docs/agents/allowed-annotations.md`
documents the common patterns as copy-paste examples.

## Consequences

What becomes easier:

- A new user runs one command and gets a curated adapter set, not the
  full list. Removing an adapter is also one command (`koment bootstrap
  --agents agents,claude` on a repo that previously installed all
  six) and the unmanaged files stay on disk if the user wants them.
- A repository with `# renovate`, protoc-gen markers or SPDX headers
  can declare them in policy and stop pretending its real allow-list
  is the Go intrinsic vocabulary.
- The contract reads as a contract. A reviewer who reads `AGENTS.md`
  and sees `MUST` understands the rule is non-negotiable without
  reading source.

What becomes harder:

- Two commands (`bootstrap`, `agents install`) now share one
  implementation. The drift between them is a future bug; both must be
  exercised in tests, and `agents install` must keep its current
  non-interactive contract because CI calls it.
- Every repository that already ran `koment agents install` will see
  a one-time managed-block diff after upgrading past this change.
  `agents check` will fail until `bootstrap` (or `agents install`) is
  re-run. The migration is one commit per repository, and the diff is
  generated text — not hand-edited — so it is reviewable as "koment
  contract refreshed".
- `allowedAnnotations` entries are regexp. A user who writes a bad
  pattern gets a `policy.Validate()` error at bootstrap time, not at
  the first commit. The schema's `pattern` is documented to require
  full regexp; a glob-only mode would be a separate proposal if anyone
  asks for one.
- A naive implementation of `koment bootstrap` could remove adapter
  files a previous run created. The implementation MUST consult
  `spec.agents.adapters` for what is selected and MUST NOT delete a
  file outside the selected set, even if a comment in the policy
  mentions it. This is part of the contract.

What this commits us to:

- The generated contract text in `agentpolicy.Contract()` is part of
  the product surface. Changing a rule there changes what every
  agent reads. The change goes through this same ADR path, even for
  wording-only edits.
- The `CONTRIBUTING.md` block body in `agentpolicy.contributingBlock(policy)`
  is generated prose, not hand-edited. It changes with the policy and
  with the contract; a human editor who changes it locally sees the
  next bootstrap revert it.
- `docs/agents/allowed-annotations.md` is part of the user-facing
  documentation. The "Common patterns" examples there are illustrative;
  the field's actual contract is the schema and this ADR. The doc
  evolves with the schema, not ahead of it.
- `spec.comments.allowedAnnotations` is part of the frozen API. Adding
  an entry to the schema is a minor change; renaming the field or
  changing its shape is breaking.
- The interactive prompt in `koment bootstrap` is a one-time onboarding
  aid. Re-running the command must never re-prompt for an adapter that
  was already selected — the policy file is the source of truth, and
  the prompt is for first contact only.
- The `CONTRIBUTING.md` managed block is treated as another adapter for
  install, refresh, drift detection and CI gating. There is no separate
  "human docs" surface to keep in sync; the same mechanism that fails
  when an agent adapter drifts fails when the human pointer drifts.

## Alternatives rejected

- **Keep `koment agents install` and add no new command.** Status quo.
  Rejected because the install path is the onboarding path today, and
  onboarding has to default to "ask me which clients I use", not
  "install everything".
- **Make `koment bootstrap` replace `koment agents install`.** Fewer
  commands; less for the user to choose. Rejected because CI,
  Lefthook and the Docker image entrypoint need a non-interactive
  scriptable form, and renaming the scriptable form is a breaking
  change for repositories that already wire it into their pipelines.
- **Make `koment bootstrap` an alias for `koment agents install`.**
  Cheapest to ship. Rejected because the gap is behaviour, not naming.
  An alias that runs the existing command reproduces the
  install-everything behaviour the user is trying to escape.
- **Prompt interactively every time `bootstrap` runs.** Symmetric and
  friendly. Rejected because the second run on a configured repo should
  refresh, not interrogate. The first run prompts; subsequent runs
  read the policy.
- **Reuse RFC 2119 keywords but keep the existing rule order and
  bullets.** Smaller diff. Rejected because the existing bullets bury
  the read-before-write rule inside "Before editing an existing file,
  call…" — a directive that an agent can read as "ask once when you
  start". The new text lifts the rule above the comment rule and
  pairs it with a `MUST`, so the structural context arrives before
  the commenting context.
- **Add a named intrinsic class for each common case (`renovate`,
  `protoc-gen`, `spdx`).** Vocabulary-shaped; familiar from
  `policy.Intrinsic*`. Rejected because the number of cases is open
  and the wording of each is not under our control. `# renovate:`
  and `Renovate-Update` are both legitimate, and the only stable
  thing is the shape of the line. A regexp on the comment body
  captures the shape without us naming the conventions.
- **Allow glob patterns (`*`, `?`) instead of regexp.** Friendlier.
  Rejected because the project's existing path-matching already uses
  glob-to-regexp translation (`policy.globExpression`), so the
  primitive is already in the codebase; introducing a second pattern
  syntax doubles the surface a reviewer has to learn for no gain a
  full regexp cannot provide. If a future user survey shows glob-only
  is wanted, that is a separate proposal that adds a `glob: true`
  per-entry flag rather than a parallel field.
- **Read the previous adapter selection from a separate
  `.koment/adapters.yaml`.** Avoids coupling selection to the policy.
  Rejected because the policy already lists adapters; a second file
  invites them to disagree, and a disagreement is harder to debug
  than a prompt the first run already settled.
- **Seed `CONTRIBUTING.md` with the agent contract itself rather than
  a human-oriented pointer.** Symmetric with the agent adapters.
  Rejected because `CONTRIBUTING.md` is a human reading surface;
  duplicating the agent contract there would either drift (two
  surfaces, same wording) or confuse the audience (humans reading
  RFC 2119 keywords). The pointer is human prose; the contract lives
  in `AGENTS.md` and the per-client adapters.
- **Make `allowedAnnotations` a discriminated union of regexp strings
  and named classes from the start, even if no named class is
  shipped.** Schema is ready for the future addition. Rejected because
  it is API surface for a use case that does not exist yet; adding
  the object form later is a minor, additive change and the ADR
  above records the path.

## Open questions

None at this point. Two deferred topics are now recorded as
decisions: the `CONTRIBUTING.md` pointer is part of bootstrap (Decision
A), and `allowedAnnotations` is regexp strings only for v1, with the
path to add named classes documented in Decision C.
